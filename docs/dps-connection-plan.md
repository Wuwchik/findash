# A.U.R.A — підключення API ДПС: безпечна архітектура

## Статус
Підготовлено майстер вибору КЕП ПриватБанку / Дія.Підпису. **Живого підключення та отримання податкових даних немає.** Жоден приватний ключ, пароль або авторизаційний заголовок не зберігається.

Документація ДПС: https://cabinet.tax.gov.ua/help/api-registers-int.html

## Вимоги ДПС
Приватні API-запити використовують заголовок `Authorization`, який містить ЄДРПОУ/РНОКПП, підписаний внутрішнім підписом із доданим сертифікатом, у Base64. Це **не OAuth-підключення**. Не можна імітувати діючу синхронізацію звичайним API-ключем.

Документовані read-only маршрути:
- `GET /ws/public_api/ta/splatp?year=2026` — стан розрахунків за платежами, зокрема `nedoim0`, `perepl0`, `debtAll`;
- `GET /ws/public_api/ta/splatp/{year}/{taxAuthorityCode}/{accountId}/pa?page=0` — деталізація рахунку;
- `GET /ws/public_api/payer_card` — облікові дані платника (податкову групу потрібно підтверджувати);
- `GET /ws/public_api/reg_doc/list?periodYear=2026&periodMonth=9` — звітність.

## Рекомендована схема, етапами
1. **Browser local sign, file КЕП:** лише vetted українська криптобібліотека з підтримкою формату КЕП ПриватБанку; локальна обробка ключа, без передачі файла/пароля до A.U.R.A, Supabase, Vercel чи зовнішніх сервісів. Провести повний security review бібліотеки; не додавати випадкові CDN-скрипти.
2. **One-shot API call:** браузер створює підписаний Authorization, безпечний authenticated backend endpoint A.U.R.A приймає його **лише в оперативній пам'яті одного запиту** й звертається виключно до allowlisted API ДПС. Усі логи, exception telemetry і analytics повинні виключати значення Authorization та персональні податкові дані.
3. **Відповідь і збереження:** зберігати за `auth.uid()` лише потрібні підсумки, час успішної перевірки, джерело `dps` і стан синхронізації у новій RLS-таблиці. Не змішувати зі старими банківськими доходами й витратами. Джерело істини для факту зарахування — ДПС, не виписка ПриватБанку.
4. **Дія.Підпис:** окреме оформлення інтеграції з Дією (https://integration.diia.gov.ua/signature.html); перевірити, чи результат підпису відповідає формату Authorization ДПС. Наявність Дія.Підпису у користувача не створює підключення стороннього сервісу автоматично.
5. **Повторне оновлення:** не обіцяти scheduled background-sync, доки ДПС не дозволяє підтвердженої, безпечної авторизації. Повторне підтвердження підпису може знадобитися щоразу.

## UX-критерії
- До успішної відповіді ДПС показувати тільки **«ДПС: ще не підключено»**.
- Не пропонувати реального upload файла ключа, якщо підписуючий SDK ще не пройшов аудиту.
- Показувати незалежні стани: `estimated`, `bank_candidate`, `user_confirmed`, `dps_verified`.
- Оплата через банк ≠ зарахування ДПС; ручна позначка не стає підтвердженням ДПС.
- Ніколи не включати прогнозовані податкові платежі в фактичні витрати на головному дашборді.
- Якщо API недоступне, залишити функціональний календар і ручну звірку.

## Заборони
- Ніякого приватного КЕП у Supabase Storage, Vercel env, localStorage, GitHub.
- Ніякого persistent JWT / Authorization із чужої державної системи для фонового доступу.
- Ніякого доступу до довільних URL у backend proxy (SSRF).
- Ніяких автоматичних платежів до ДПС без окремої явної дії користувача.

## Автоматичне відображення податкових платежів (етап browser-only)
- Коли A.U.R.A відкрита, список банківських операцій оновлюється через читання Supabase раз на 60 секунд. Фактична затримка залежить від синхронізації ПриватБанку з Supabase.
- Тільки списання типу `expense` з підтвердженим видом податку та **явним кварталом у призначенні** автоматично відносяться до цього кварталу.
- Якщо сума списань досягла прогнозованого зобов'язання, показується **зелена позначка «Оплачено через банк»**. Неповна сума має жовтий статус, невідома база — «суму не визначено».
- Для платежів, у яких квартал відсутній, користувач може сам прив'язати одну банківську транзакцію до однієї податкової події. Платежі з явним *іншим* кварталом не пропонуються. Налаштування прив'язки RLS-захищені.
- Ручний прапорець «Я оплатив», банківська зелена позначка і майбутній стан **«Зараховано ДПС»** залишаються трьома окремими статусами. Не слід позначати податкове зобов'язання як офіційно сплачене лише на підставі прогнозу.
- Не створювати окремі `expense`-транзакції в основному фінансовому дашборді: це подвоїть фактичні списання; розділ «Податки» є представленням уже наявних операцій.

## Сповіщення, поки A.U.R.A відкрита
- Кнопка «Увімкнути сповіщення» викликає системний дозвіл браузера тільки по кліку; HTTPS обов'язковий.
- Нагадування про строки: за 14, 7, 3, 1, 0 днів і контрольні повтори після прострочення, окремо за кожен податок/період; збережено захист від повторів на кожному пристрої.
- Сповіщення «Оплачено через банк» — тільки коли вперше з'явилося повне зіставлення; старі платежі під час першого ввімкнення не створюють шквал повідомлень.
- Нагадування працюють у всіх вкладках A.U.R.A, а не лише у вкладці «Податки».
- Зараз **це не Web Push після закриття сайту**. Для цього потрібен VAPID/Service Worker, push-підписки, серверний розклад і перевірка підтримки браузером.
